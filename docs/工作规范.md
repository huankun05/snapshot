# 工作规范

> 本工作区（拾花 PetalSnap，`F:\Work\Create\OCR\screenshot`）所有开发任务遵循的流程与约定。
> 每个任务无论大小都走完九步；小任务可以几步合并在一次对话里完成，但**不跳步**。
>
> 创建：2026-09-15

---

## 一、九步流程

| 步 | 名称 | 产出 | 通过门槛 |
|---|---|---|---|
| 1 | **写方案** | `docs/` 下设计文档或功能状态清单中的条目：目标、涉及文件、改动要点、验证方式、风险 | 方案能让第三人不看代码就知道要改什么、怎么验证 |
| 2 | **确认方案** | 用户明确同意（"按这个来"/"OK"） | **未确认不写代码**；用户提出修改则回到步 1 |
| 3 | **写代码** | 按方案改动；遵守 §三 代码约定 | 构建通过（`cd app && node build-host.js`） |
| 4 | **审查代码** | 自审 diff：边界条件、错误路径、dpr>1、IPC 协议兼容、i18n 双语、与方案是否一致 | 审查发现的问题当场修，记录到步 7 的变更说明 |
| 5 | **测试** | 按 §四 回归清单实测，涉及长截图跑 `tools/` 三套回归 | 所有涉及面实测通过；失败项如实记录，不粉饰 |
| 6 | **完善** | 根据测试结果修复、补漏、调优；必要时回到步 3 | 无已知阻断性问题 |
| 7 | **更新文档** | `功能状态清单.md`：待实现 → 已实现（日期+验证方式）、变更日志加行；相关设计文档同步 | 文档与代码一致 |
| 8 | **整理文件夹** | 删除临时/测试产物；两份 `rapidocr_service.py` 同步；新增资源放对目录 | `git status` 中没有不该入库的文件 |
| 9 | **提交仓库** | 单主题提交 + 推送 origin/main | 提交信息符合 §五 规范 |

## 二、文档约定

- **`docs/功能状态清单.md` 是单一事实源**：功能现状、待实现、调研结论、变更日志全在这里；
  其他文档是它的展开（`长截图问题排查记录.md`、`Shotera竞品调研.md`、`UI设计方案.md`、
  `设置面板设计.md`、本文）
- 每完成一项：条目从「待实现」移到「已实现」并注明**日期 + 验证方式**；变更日志加一行
- 新需求先进「待实现」，再写方案；调研结论进「四、调研结论」
- 设计文档中的「待拍板」项一旦用户决定，**当场改成已定并注明日期**，不留悬空
- 文档用中文，术语首次出现给英文/代码标识（如 accent、`store:read`）

## 三、代码约定

- **风格跟随现有代码**：主进程 TypeScript（`main/`、`app/`），渲染端纯 JS + HTML + CSS
  （`resources/`），无框架、无打包器依赖新增；新页面与 capture/pin 同构
- **注释只写代码看不出来的约束**（为什么这么做、历史坑），不写"这行做了什么"
- **零新运行时依赖**原则：图标内联 SVG、i18n 内联字典；确需新依赖先在方案中说明
- **i18n 双语**：capture.js / pin.js / settings.js 的内联字典 zh/en 同时补齐
- **IPC 协议是与 Xiyue 的耦合面**：通道名与数据格式改动必须在方案中标注（移回时要对账）
- **store 键**沿用 `shared/storeKeys.ts` 既有键名；新键在该文件登记并写注释
- 设计令牌只用 CSS 变量（`--ui-*`，见 `UI设计方案.md` §2.3），不新增硬编码颜色
- **不放死设置/死按钮**：依赖未实现功能的 UI 不渲染
- Python 服务：`rapidocr_service.py` 根目录与 `ocr-service/` 两份**必须同步**（diff 为空才算完成）

## 四、测试回归清单

每次改动按涉及面勾选实测（构建 → 启动 → 手测）：

- [ ] **启动**：单实例锁、托盘出现、热键注册（含备用键链）、OCR 服务预热日志正常
- [ ] **区域截图**：拖选、悬停窗口选中、尺寸标签、150% 缩放下裁剪不偏移（r61 回归点）
- [ ] **标注十工具**：马赛克/模糊/噪点/纯色/矩形/直线/箭头/椭圆/画笔/文字各画一次，撤销重做
- [ ] **输出**：保存、复制剪贴板、贴图（缩放/拖动/关闭）
- [ ] **识别**：文字 / 表格 / 智能三档各一次，结果面板预览与复制；冷启动与热态各一次
- [ ] **翻译**：本地端侧一次（含原文/译文切换）；换目标语言后重翻
- [ ] **长截图**：入口可进可退（滚动拼接质量问题按 `长截图问题排查记录.md` 单独跑
  `tools/` 三套回归：42/17/5 全绿为基线）
- [ ] **设置**（有设置窗后）：每项改动即时生效并持久化，重启后仍在
- [ ] **UI**：浅色/深色桌面内容上工具栏均可读；多屏与 dpr 混合下位置正确

测试结论如实写入变更日志（"实测通过"/"未测"/"X 项失败待修"），**不把未测写成通过**。

## 五、提交规范

- 格式沿用现有历史：`类型(范围): 中文摘要；分号分隔多个要点`
  类型：`feat` / `fix` / `perf` / `docs` / `chore` / `refactor` / `style`；
  范围可选：`translate` / `table` / `ui` / `settings` / `ls`（长截图）等
- 摘要写**做了什么 + 为什么**（根因/动机），例：
  `fix(ui): 面板底部语言行不再强制独占一行——优先与按钮同行，极窄时收缩/折行兜底`
- **一个主题一次提交**；文档更新可随功能一起提交，也可单独 `docs:`
- 提交前 `git status` 确认无临时文件；推送 `origin main`
- 不提交：`node_modules`（软链）、模型文件、日志、测试截图、`__pycache__`

## 六、文件夹约定

```
screenshot/
├─ app/            独立应用宿主（main.ts、settings.ts、build-host.js、dist/）
├─ main/           主进程模块（ipc/ window/ services/ config/）
├─ resources/      渲染端页面与静态资源（capture/pin/settings 的 html/js/css、icon/、svg/）
├─ shared/         主/渲染共享（storeKeys.ts）
├─ ocr-service/    Python 识别服务（与根目录 rapidocr_service.py 同步）
├─ tools/          长截图回归工具链
├─ docs/           全部文档
└─ README.md
```
- 临时实验脚本放 `tools/scratch/`（gitignore），验证完毕删除或转正
- 测试图片不入库；需要的固定用例放 `tools/fixtures/`
- `F:\Work\Create\OCR` 根目录是历史迭代与 Python 环境所在，不再新增文件（除 `rapidocr_service.py` 同步）
