## 一、我们现在的方法（三层，各有硬伤）

| 层 | 实现 | 本质 | 缺陷 |
|---|---|---|---|
| level 0（默认） | `capture.js::detectUiElementAt` **墨迹投影**：以光标为锚找文字墨迹行 → 行距合并成段 → 列投影扩宽 → 加 padding | **文字块探测器**，不是"界面元素探测器" | 对"头像+标题+预览+时间"的复合行只能连成一整块；框的大小随墨迹分布漂移；无 UI 语义 |
| level ≥1（滚轮放大） | `smart_uia.dll` 原生 UIA 层级链（RawView 钻取 + 上溯 + 去重） | **无障碍树查询** | 覆盖率问题（见 §二）：Chromium 要先激活、自绘应用树粗或不稳、游戏完全没有 |
| 窗口级 | Win32 `WindowFromPoint` + z 序扫描（跳过自身） | 顶层窗枚举 | 只有大框，无细分 |

结论：**默认显示的"智能框"来自最弱的启发式（墨迹投影），最强的 UIA 只用来放大**——架构倒置。

## 二、Shotera 用什么（exe 字符串取证，2026-09-17）

`shotera.exe` 内可见的检测栈（无任何 OpenCV/像素分析字符串）：

- UIA 全家桶：`CoCreateInstance(CUIAutomation)`、**`CUIAutomation8`**（IUIAutomation2+ 接口）、
  `CreateCacheRequest(RawView)`、`RawViewWalker`、`FindAll` + TrueCondition、
  `AccessibleObjectFromWindow`（MSAA 双通道）
- **按框架特判**：日志串 `[UIA] Chromium render hwnd=0x…`、`[UIA][chromium]`、`[UIA][explorer]`、
  `[UIA][taskbar]`、`WebView2: skipped inaccessible`——对 Chromium 渲染窗、资源管理器、任务栏分别有
  专门处理（Chromium 大概率是定位渲染子 HWND 直接对它建 UIA 会话，绕过"整窗树未激活/过粗"）
- 工程化细节：`[UIA] target changed old=…`（目标变化跟踪）、`[UIA][timing] capture/prepare/query`
  （分级计时）、设置项 `detect_ui_element` / `uia_hover_anim_ms`（**用跟随动画掩盖查询延迟**）

**结论：Shotera 是纯 UIA 路线，"准"靠的是多年按框架逐个适配积累**（Chromium/Explorer/任务栏…
每个都是特例），再用动画把残余延迟/跳变抹平。这条路线我们短期追不平适配量，且天花板受制于
各应用的无障碍实现质量（微信/QQ/游戏仍是弱区）。

像素为主。我们两样都沾但都只做了一半，各取了对方的短板。

## 四、为什么我们不准（直接回答）

1. **默认级的像素法是"墨迹投影"，不是"矩形检测"**：它按文字墨迹的行/列分布扩展再加 padding，
   得到的是"文字块"而非"界面元素"。复合行、图标、大面积留白、同色块背景都会让它漂移。
2. **UIA 天花板受制于各应用**：Chromium 无障碍要异步激活（首查粗）；微信/QQ 自绘框架树粗或矩形
   不稳；游戏没有。Shotera 用框架特判 + 动画掩盖才把 UIA 路线做到"可用"，仍不解决微信粒度问题。
3. **架构倒置**：最弱的启发式承担了默认展示，最强的像素信息反而没用上——截图工具最大的优势就是
   **手里有这一帧的完整像素**，Snipaste/微信的"准"全部来自对它的分析。

## 五、修改方案：像素矩形层级检测（C++，对齐 Snipaste/微信路线）

### 5.1 核心思想
截图帧已在手（bgCanvas 的物理像素 buffer）。**"光标所在的界面元素"= 屏幕上以光标为内点、
四边都对齐强边界的最小矩形**，逐级向外扩大（文字/图标 → 行/卡片 → 面板 → 主窗）。
边界完全来自像素本身，**所见即所得**，不依赖任何应用的实现质量——这正是 Snipaste/微信
"处处准"的原因。

### 5.2 算法（在 `smart_uia.dll` 内新增导出，符合 C++ 性能诉求）
```
SmartPixelDetectLevels(const uint8_t* bgra, int w, int h, int stride,
                       int px, int py, char* outJson, int cap) -> int
```
1. **边界信号**：对每个像素算与"局部背景色"的差（光色差 + 亮度差），二值化为边界图；
   局部背景取光标所在均匀区域的主色（吸附式页面背景不再是噪音）
2. **四向边界搜索**：从光标行/列分别向上下左右扫第一个强边界（连续 ≥k 像素的边界带），
   得到最内层矩形的候选四边；边界带用积分图 O(1) 查询区间和，整屏扫描 O(W+H)，
   实测目标 **<1ms**（C++ 单线程，2560×1440）
3. **层级外扩**：从最内矩形逐级向外找下一圈边界（同法），生成 4~8 级矩形链，
   每级四边都对齐真实边界——滚轮切层"每步都贴着一条真实边"
4. **一致性校验**：候选矩形内部用积分图判方差，方差过大的候选（横跨图文混排区）丢弃，
   防止框"半行"
5. **UIA 降级为语义增强**（可选，二期）：对像素矩形中心再查一次 UIA，只为放大镜显示
   控件类型/名称，不再决定框的位置

### 5.3 数据通道
- 截图帧：capture.js 已有 `bgCanvas`（物理分辨率 RGBA），经 IPC 把 buffer 传主进程
  （一次会话传一次 + 滚动/长截图时更新；拖动中只传光标坐标，帧不变）
- DLL 内不再做任何 UIA 调用于热路径；`SmartUiaGetLevels` 保留给"控件名"增强与降级

### 5.4 风险与对策
| 风险 | 对策 |
|---|---|
| 相邻同色块之间无强边界（真 UI 也有这种行） | 多信号边界（色差/亮度差/纹理差），无边界时该级自然不存在——回到上一级，行为可预期 |
| 边界带宽度不一（1px 细线 vs 阴影渐变） | 边界判定用"带"而非"线"（k 像素容差），阈值按 dpr 缩放 |
| 帧传输成本 | bgCanvas 物理帧一次 ~14MB，仅会话开始/内容变化时传；hover 热路径零传输 |
| 算法调参工作量 | 这是真实存在的迭代成本（Snipaste 作者打磨多年），用固定场景回归清单（微信列表/Edge/资源管理器/ZCode/任务栏/桌面）逐个过 |

### 5.5 实施顺序（确认后开工）
1. **P1**：DLL 新增 `SmartPixelDetectLevels`（边界图 + 四向搜索 + 层级外扩 + 校验），
   渲染端 level 0/1 全部切到像素层级；UIA 链保留为滚轮向外扩展的补充（或完全停用，实测定）
2. **P2**：六场景回归调参（微信列表 / Edge / 资源管理器 / ZCode / 任务栏 / 桌面），
   每场景截图留档对比
3. **P3（可选）**：UIA 语义增强（放大镜显示控件类型/名称）

### 5.6 P1 实施记录（2026-09-17 完成，待用户实测）
- **C++**（`smart_uia.cpp` 重编）：新增 `SmartPixelFramePrepare(rgba,w,h,stride)`（主色=16 级量化直方图
  众数、前景掩码=通道差和>90、积分图，1505×365 帧实测 3ms）与 `SmartPixelDetectLevels(点+边界)`，
  间隙阶梯 {4,12,24,48,96,192}×分辨率缩放做 xy-cut，级间去重；UIA 导出原样保留。
- **离线验证**（`tools/pixel_probe.js` + 表格截图回绘目检）：文字 177×23 → 单元格 187×33 → 列块
  323×278 → 整表 1462×353 层级全部吸附真实边界；单次查询 **0.03~0.16ms**，Prepare 3ms。
  注意：用户微信截图属"活屏裁剪"（带暗蒙版/选区框/放大镜），不能作离线帧——须用干净截图。
- **接线**：`smartUiaNative.ts` 加两个像素导出；`main.ts` 新增 `smart:frame`（会话一次，帧入 DLL 缓存）
  与 `smart:pixel-at`（物理坐标进出，转 DIP 回渲染端）；`capture.js` 在 `drawBackground` 后
  `sendSmartFrame()`（按尺寸+会话去重，新会话/长截图拼接强制重发），`requestSmartPixel`（16ms 节流

- 已知取舍：多显示器下帧坐标系与 UIA 路径相同（虚拟屏物理帧）；同色相邻块间无强边界时该级自然
  不存在（回到上一级）——强边界切割信号（梯度积分图）留作 P2 调参项。

## 六、P1 实测复盘：间隙阶梯法为什么仍然不精确（2026-09-17，用户二次反馈）

### 6.1 现在的框是怎么算出来的（坦白版）
当前 level 0 = `SmartPixelDetectLevels` 的**间隙阶梯 xy-cut**：
1. 对整帧求"前景掩码"：像素与**全帧主色**的通道差和 > 90；
2. 从光标出发，按间隙容差阶梯 {4,12,24,48,96,192}px 逐级扩展：行带扩展（行内前景计数，连续空行
   ≤ g 就继续吞）→ 列带扩展 → 加 padding 成一级矩形。

**它本质仍是"文字块连通域"，不是"边界检测"**。三个精度天花板（结构性，调参救不了）：
1. **边界不在"间隙"上，在"边"上**。真实 UI 元素的视觉边界是 1px 描边、分隔线、色块突变；
   间隙法只在"空白带"处停，所以框的边落在"最后一个字"+padding 上，而不是元素的框线上——
   悬停行尾部有空白时，框比可见边界小；行与行之间只有 1px 分隔线没有空白带时，直接穿过。
2. **全局主色当背景，多背景屏幕必翻车**。微信窗口 = 白色列表 + 深色侧栏 + 灰色悬停带 + 聊天区，
   主色只能是其中一个；悬停灰带 (#E6E6E8) 与白底差 ~73 < 阈值 90 → **视觉上行就是灰带，算法眼里
   它是背景**，框永远吸附不到灰带边界；深色侧栏又是超强前景，一旦并进来就拖到全宽。
3. **阶梯是离散的，真实间隙是连续的**。行间隙 25px 落在阶梯 24 和 48 之间：24 框不住整行、
   48 越过行吞进下一行——"选到精确元素"需要边界**对齐**，而不是凑整。

表格截图离线验证能过，是因为深底+亮字+清晰表格线恰好是间隙法最舒服的场景；真实应用界面
（微信/浏览器）到处是"弱边界+多背景"，天花板立刻暴露。

### 6.2 Shotera 为什么框得准（对比结论）
Shotera = **UIA 元素矩形**：框直接来自应用自己的 UI 提供方（按钮/列表项/网页元素的真实 bounding
rect），天然像素级对齐——这不是算法好，是**答案抄自应用本身**。它的工程量都在弥补 UIA 的覆盖面：
Chromium 渲染窗特判、Explorer/任务栏特判、MSAA 双通道、动画掩盖延迟。代价：无障碍树没有的
地方（游戏、部分自绘）就没框；且各应用实现质量参差。

Snipaste = **纯像素边界检测**：框吸附在图像里真实的边（描边/分隔线/色块边界）上，与任何 API 无关。
它"准"的定义是**对齐视觉边界**，天然全场景一致。

我们前两版各学了半截：UIA 版学 Shotera 但没做框架适配（还踩了 DPI bug）；像素版做的是
"文字连通域"而非"边界检测"——两版都到不了"精确"。

### 6.3 修改方案（P1 重做检测核心；P2 恢复 UIA 优先+像素校验）
**P1a：间隙阶梯 → 边界吸附矩形检测**（DLL 内替换，接口不变）
- Prepare 增加两套积分图：水平梯度 Gh（|px(x)-px(x-1)| 通道和）与垂直梯度 Gv
- 定义两类可停靠边界（行/列各一套，均为 O(1) 区间查询）：
  - **强边**：边界线跨越当前跨度 ≥60% 的行/列有强梯度（1px 描边、分隔线、面板描边）
  - **静默带**：连续 ≥q 行/列前景≈0 且梯度≈0（纯空白分隔）
- 检测：从光标四向扫描，**遇到的第一个"强边"或"静默带"即为该方向的边**（强边优先且吸附到线上）；
  四边齐 → 最内层矩形；此后每边向外找下一条强边/静默带 → 逐级外扩成层级链（每级四边都在真实边上）
- 多背景免疫：强边不依赖任何"背景色"假设；同色相邻块（无边界）该级自然不存在，行为可预期

**P1b：level 0 恢复 UIA 优先 + 像素校验**（两全）
- UIA 最深元素存在、含光标、面积 <30% 屏 → 用 UIA（元素语义精确，Shotera 路线）
- 否则用 P1a 像素层级（Snipaste 路线兜底，自绘/游戏/未激活场景）
- 校验：UIA 矩形若与像素强边明显错位（未来可加），当前先信 UIA 的 contains 约束

**P2（浏览器精度的补刀，可选）**：学 Shotera 对 Chromium 渲染子 HWND（Chrome_RenderWidgetHostHWND）
做 `AccessibleObjectFromWindow` 戳一下强制激活无障碍，消除"首查粗、几帧后才收敛"。

### 6.4 验收
微信列表：悬停行 → 框=行（对齐行背景带边界）；标题/头像 → 文字/头像块。Edge：按钮/图片独立成框。
资源管理器：文件行。所有框的边与屏幕上可见的线/色块边界对齐。

### 6.5 P1a/P1b 实施记录（2026-09-17 完成，待用户实测）
- **P1a 已落地**：Prepare 增加 gmh/gmv 强边界掩码（相邻像素通道差和 ≥96，饱和防溢出）+ 两张积分图
  （Prepare 3→6ms）；检测改为**边界吸附**——每条边独立扩展，先到先停：强边（该列/行在当前跨度上
  ≥60% 为强边界像素，吸附到线上）或静默带（连续 ≥quietMin 无前景）；quietMin 阶梯
  {3,10,22,44,88,176}×分辨率逐级放宽 → 静默停靠的边在下一级穿过更宽空白吸到更外层的强边。
  强边判定要求跨度 ≥12px（细带噪声不参与）。离线验证：表格截图上框紧贴文字运行/列边界/整表
  （"表头并成一个格"177×23 红、问题列青、整表洋红全对齐），单次 0.4ms。
- **P1b 已落地**：渲染端改为**合并层级链** `getMergedSmartLevels()` = 像素边界链 ∪ UIA 元素链
  （面积升序、四边 ≤4px 近重复去重、自动补窗口级与屏幕级）——UIA 元素矩形精确时它是链里最小的
  （level 0），自绘/未激活场景由像素链补位，不再非此即彼。`cycleSmartLevel` 同步切换；
  悬停两路并发请求（各自 16ms 节流）。
- 原生 UIA 层、Python /uia（已 DPI 感知）保留为合并链的数据源之一。
