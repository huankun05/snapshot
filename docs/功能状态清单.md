### 3.10 进程 / 资源生命周期安全（2026-11-02「整机崩溃」事故专章）

**事故**：用户报「电脑崩了」，怀疑是本项目改动导致 llama-server 反复重启、累积占满显存。

**根因链（三段，逐段实锤）**：
1. **触发源（我的责任）**：本轮所有探针脚本（`_local_path.ps1` / `_follow_probe.ps1` /
   `_morph_curve.ps1` / `_scan_targets.ps1` / `_latency_ab.ps1` / `_latency_cross.ps1`）
   每次运行都用 `Get-Process ... | Stop-Process -Force` 杀应用 → Windows 上强杀 =
   TerminateProcess → 应用**来不及跑自己的退出清理**。
2. **放大器（产品缺陷）**：宿主只杀 python 侧车一个进程，而 Windows 上
   `proc.kill('SIGTERM')` / `std::process::Child::kill()` 都是 TerminateProcess
   → **python 的 atexit 不执行** → `mt_engine.shutdown()` 不跑 → 它拉起的
   `llama-server.exe`（Hy-MT2，**~1.2GB 显存/个**）变**孤儿**继续占显存。
   仓库外 `rapidocr_service.py` 的孤儿清理依赖 `wmic`——**本机 Win11 已移除 `wmic.exe`**
   → except 分支静默跳过 → 清理从未真正生效；F1 侧 `local_capture_service.py` 则
   **根本没有**孤儿清理。⇒ 每跑一次探针就多留一个 llama-server。
3. **正反馈**：显存被孤儿挤占 → `mt_engine` 看门狗「连续 5 次慢 → 重拉 llama-server」
   → 用户看到的「一直重新启动」；本机 RTX 4070 Laptop **仅 8GB**，6~7 个即打满
   → CUDA 分配失败降级共享内存 → 系统内存雪崩 → 整机崩溃。

**修法（四道，按可靠性排序）**：
- ✅ **F2 根治：Job Object + `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`**
  （`tauri-spike/src-tauri/src/main.rs`）：侧车 spawn 后 `AssignProcessToJobObject` 收进 Job
  → **宿主进程一消失（哪怕被 TerminateProcess 强杀）→ OS 连树陪葬**（python + llama-server）。
  这是 Windows 上唯一能对抗「宿主被强杀」的手段——依赖 python atexit 靠不住。
  **手写 Win32 ABI**（`mod jobobj`）而非用 windows crate：依赖树里有两份 `windows_core`
  （0.58 与 0.62），`PCWSTR` 在 0.58 是类型别名、0.62 是结构体 →
  `CreateJobObjectW` 的泛型参数推不出类型（E0271/E0277：expected CopyType, found InterfaceType）。
- ✅ **双端回收改连树杀**：F1 `localOcrMtService.ts` 的 `stopLocalOcrMtService()` 与
  启动超时分支、F2 的 `kill_py_service()`，一律改 `taskkill /PID /T /F`（连子孙进程）。
- ✅ **启动前清扫历史残骸**：新增 `tools/_sweep_orphans.ps1`——**判据 = 父进程已不存在**
  （用 PowerShell CIM，**不用已被 Win11 移除的 wmic**）；宿主启动时 + 拉起侧车前各调一次。
  F2 把脚本**编译期内嵌**进二进制（`include_str!`），不依赖运行目录布局。
  「父进程已死」这个判据同时保证：**用户手动 run.bat 起的实例不会被误杀**（父进程 cmd 存活）。
- ✅ **不再重复拉起**：端口有人监听但 `/health` 不通（侧车正忙）时**等**而不是再拉一个
  ——第二个侧车会再拉一个 llama-server。F2 原 `/health` 探测超时只有 **400ms**，
  侧车加载模型期间必然误判 → 正是重复拉起的入口。

**探针脚本整改**：全部 `Stop-Process -Force` → 统一走新增的 `tools/_stop_app.ps1`
（优雅停 → `taskkill /T` 树杀 → 孤儿清扫），并改用**当前 PowerShell 宿主**再起子进程
（保证与调用方同一版本）。

**验证**：
- `cargo test` **3/3 通过**：①Job Object 机制（assign → 关句柄 → 树被带走）；
  ②**生产路径**——`spawn_py_sidecar()` 真的把侧车收进 Job（用 dummy 脚本冒充
  `rapidocr_service.py`，不加载模型秒起，测完即回收）；③端口监听判定。
- 清扫脚本实测：造 4 个真孤儿（伪 `llama-server.exe` + 伪侧车 python，父进程已死）
  → `killed=4`、**残留 0**；Windows PowerShell 5.1 与 pwsh 7 **双跑均通过**。
- `_stop_app.ps1` 实测：停应用后 `appLeft=0 llamaLeft=0`。
- F2 启动日志实测：`[py] SWEEP orphan sidecars: llama=0 sidecar=0 killed=0`。

**踩坑（值得记）**：
- ① Windows PowerShell 5.1 读**无 BOM** 的 `.ps1` 会按 ANSI(GBK) 解码 → 中文注释解码错乱
  → **脚本解析异常 → `taskkill` 根本没执行，且没有任何报错**（实测 `killed=0`、进程还活着）。
  本仓库 `.ps1` 惯例是无 BOM（探针本来就要求 pwsh 7），但清扫脚本会被**宿主直接调用**
  （宿主环境不保证有 pwsh 7）→ 该脚本**单独加 UTF-8 BOM** 双保险；宿主导出侧改成
  「优先 `pwsh.exe`，退回 `powershell.exe`」。
- ② `include_str!` 会把文件**自带的 BOM** 当成 U+FEFF 读进来 → 临时文件写成**双 BOM**
  → PowerShell 解析出错 → 必须在拼接前 `strip_prefix('\u{feff}')`。

**✅ 补做：仓库外侧车自身的加固**（`F:\Work\Create\OCR\`，不在 git 内，但 `edit` 工具可改 → 已直接改好）
- `screenshot_tool/mt_engine.py`：`shutdown()` 由 `terminate()/kill()` 改为
  **`taskkill /F /T /PID`**（连 llama-server 的子孙进程一起杀）。
- `local_capture_service.py` / `rapidocr_service.py`：新增**父进程死亡守护**
  （`_pid_alive()` + `_parent_watchdog()`）：宿主消失 → 回收 llama-server → 自己退出。
  探活用 `OpenProcess(SYNCHRONIZE) + WaitForSingleObject(h, 0)`（纯 ctypes，不加依赖）。
- `rapidocr_service.py` 的 `_kill_orphan_llama_servers()`：**wmic → PowerShell CIM**
  （判据与 `tools/_sweep_orphans.ps1` 同源：父进程已不存在 = 孤儿）。

**★★★ 这里挖出一个此前完全没人知道的平台事实（很可能推翻很多想当然的设计）**：
> **本机 `venv_ocr\Scripts\python.exe` 是「转发器」——它自己会再拉起一个真正的解释器进程。**
> 实测：宿主 `subprocess` 拿到的 `Popen.pid`（= 转发器 PID）≠ 子进程自己的 `os.getpid()`
> （= 真解释器 PID）；真解释器的 `os.getppid()` = **转发器**的 PID。

由此推出三条**必须记住**的结论：
1. **侧车的直接父进程不是宿主应用**，而是那个转发器。⇒ 任何「盯 `os.getppid()` 判断宿主
   是否还活着」的守护**永远不会触发**（宿主被强杀时转发器还活着，它在等侧车退出）。
   ⇒ 宿主必须**显式传自己的 PID**：本次新增环境变量 **`PETALSNAP_OWNER_PID`**
   （F2 Rust `spawn_py_sidecar()` 与 F1 `localOcrMtService.ts` 均已注入）。
2. **Windows 上父进程死后子进程不会被 reparent**（`InheritedFromUniqueProcessId` 保持原值）
   ⇒ 判据只能是「父进程 PID 是否还活着」，不能看 `getppid()` 有没有变。
3. **`os.kill(ppid, 0)` 在 Windows 上会 `TerminateProcess` 父进程**（CPython 把非
   CTRL_C/BREAK 信号一律映射成 TerminateProcess）⇒ **绝对不能**用它探活，会误杀宿主。

**⇒ 连带修正了 Job Object 的验收标准**：宿主 spawn 出来的是转发器，**真正跑侧车逻辑的是
孙进程**。若孙进程没继承 Job，Job 就只护住了转发器、侧车本体照样变孤儿。
回归测试因此升级为**必须断言孙进程也随 Job 一起死**（判据决定性：Windows 上父进程被 kill
**不会**连带杀子进程 → 孙进程死了就只可能是被 Job 连带杀的）。**实测通过**。

**一键自测**：`tools/_process_selftest.py`（不加载任何模型，秒级完成）—— A 三个仓库外文件
语法编译 / B `_pid_alive` 三态 / C 父进程消失 → 侧车自杀（端到端）/ D CIM 清理正负两测 /
E 收尾无残留。可用 `--with-cargo` 一并跑 F2 的 Job Object 回归测试。

### 4.1 识别模型选档 —— 现状最大问题：我们用的 tiny 档精度不足

RapidOCR 官方博客（2026-06）CPU 实测（ExactMatch / 耗时秒）：

| 模型 | 框架 | ExactMatch | CharMatch | 耗时(s) |
|---|---|---|---|---|
| PP-OCRv6_medium | RapidOCR+ONNX | **0.8613** | 0.9491 | 0.0515 |
| PP-OCRv6_small | RapidOCR+ONNX | 0.8419 | 0.9515 | 0.0143 |
| PP-OCRv6_tiny | RapidOCR+ONNX | 0.6968 | 0.8897 | 0.0030 |
| PP-OCRv5_server | RapidOCR+ONNX | 0.8129 | 0.9431 | 0.0655 |

- **我们 PP-StructureV3 管线当前配的是 v6_tiny det/rec**（layout_worker.py 默认值）——精度垫底。
- v6_medium 以 73M 体积超越 v5_server（精度 +5.1%、检测 +4.6%），单模型统一支持中英日等 50 语言。
- 52pojie 帖的「PaddleOCR-V6-Portable」即此路线（PP-OCRv6_medium ONNX + 网页界面 + xlsx 导出），闭源，
  但证明 PP-OCRv6 ONNX CPU 推理做离线截图 OCR 完全可行。

### 4.2 排版还原 —— 两条候选路线

| 路线 | 组成 | 优势 | 代价 |
|---|---|---|---|
| **A. rapid-doc**（RapidAI） | MinerU 精简管线：PP-DocLayoutV3（自带阅读顺序）+ PP-OCRv6-small + PP-FormulaNet + 表格模型，全 ONNX CPU | OmniDocBench 90.157（超 MinerU-Pipeline 86.47 / Marker 78.44）；输出 Markdown/JSON/HTML；`pip install rapid-doc[cpu]` | 模型多、首次下载大；截图（非文档）场景可能过重 |
| **B. RapidOCR + 排序算法** | RapidOCR(PP-OCRv6) 文本块 + PP-DocLayout 版面分类 + GapTree/xy-cut 阅读 order 排序 | 轻量、可控；GapTree 为 Umi-OCR 作者开源纯算法（多栏报刊式排版强项） | 排序/结构化需自己拼装 |

- 现有 PP-StructureV3（paddle 全家桶）已知问题：CPU 内存泄漏/占用过大（PaddleOCR issue #15738）、
  整线多模型导致 CPU 极慢——这就是此前"没成功过"的原因，**方向应换成 ONNX 轻量栈**。
- 截图场景与 PDF 文档场景不同：截图多是 UI 界面（多栏卡片/侧栏/图标），PP-DocLayout 系列按文档训练，
  UI 截图效果需实测；GapTree 对 UI 多栏卡片可能更贴。

### 4.3 图标识别/过滤 —— 业界三层方案

1. **识别前**：忽略区域（Umi-OCR 方案）——适合用户手动排除水印/按钮，不适合全自动；
2. **识别中**：版面模型分类过滤——PP-DocLayout 系列原生输出 figure/icon 等元素标签，
   图标区域直接排除或占位（推荐，随 §3.2 顺带落地）；
3. **识别后**：置信度阈值 + 启发式（宽高比、笔画密度）+ 规则过滤。
- 参考：Umi-OCR 忽略区域、GapTree_Sort_Algorithm、PP-DocLayoutV2 阅读顺序解码（win-accumulation）。

### 4.4 本机实测数据（2026-09-12，venv_ocr + rapidocr 3.9.2，真实截图帧 1526×672 等 3 张）

| 配置 | warm 耗时/张 | 识别质量 |
|---|---|---|
| PP-OCRv6 small（默认，cls 关） | **~1.58s** | 好：终端命令、长段落、中英混排均准确 |
| PP-OCRv6 small（默认配置） | ~1.75s | 同上 |
| PP-OCRv6 medium | 12.8~19.1s | 仅多空格级优化，速度不可接受，弃用 |
| （对照）现管线用的 v6_tiny | 官方数据 ExactMatch 0.697 | 精度垫底，确认弃用 |

- 结论：**PP-OCRv6 small 是本机 CPU 的正确选档**；模型随 whl 内置（29.5MB），无 paddle 依赖。
- 路线 B 拼装验证（`OCR/test_layout_b.py`）：RapidOCR 文本框 + 既有 `_group_paragraphs`
  → 文本页段落分组效果好（阅读顺序正确、续行正确合并）；
  UI 截图中按钮/图标文字成为独立噪音段落 → 引出 §3.3 图标过滤项。
- 验证脚本：`OCR/test_rapidocr_v6.py`、`OCR/test_rapidocr_bench.py`、`OCR/test_layout_b.py`。
